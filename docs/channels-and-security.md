# 接入方式、安全设计和代理

数据存在哪、发给谁，以及员工监控、客户告知和各地法规，见[合规指南](compliance.md)。

## 接入方式的区别和风险

墨鸽支持 WhatsApp（扫码、Meta 官方接口）、LINE 官方帐号和 Telegram（机器人、Business、扫码登录）共六种接入方式。Telegram 的三种见下面的 [Telegram](#telegram)。

| | 扫码（WAHA） | Meta 官方 Cloud API | LINE 官方帐号 |
|---|---|---|---|
| 原理 | 模拟 WhatsApp 网页版 / 关联设备，走**非官方协议** | Meta 官方的企业接口 | LINE 官方的 Messaging API，客户加你的官方帐号为好友后在 LINE 里聊 |
| 准备 | 一部装了 WhatsApp 的手机，扫码即可 | Meta 开发者账号、企业验证、专用号码、公网 HTTPS 回调 | LINE 官方帐号、在 LINE Developers 开通 Messaging API、公网 HTTPS 回调 |
| 风险 | **有封号风险**：WhatsApp 不允许非官方客户端，号码可能被限制或封禁。批量群发、短时间大量回复、新号都会加大风险 | 走正规渠道，没有协议层面的封号风险；但要遵守 Meta 的商业政策和 24 小时客服窗口（客户 24 小时内没发过消息时，只能发模板消息） | 走正规渠道，没有协议层面的封号风险；但只能和加了好友的人聊，不能按手机号找人，所以没有外联群发；要遵守 LINE 官方帐号的使用规定 |
| 费用 | 自建 WAHA，不按消息计费（WAHA 分免费的 Core 版和付费的 Plus 版） | 按 Meta 的定价计费 | 收到消息 1 分钟内的回复不计数；之后发的（人工回复基本都是）算「推送」，计入官方帐号方案的每月额度。免费方案每月只有几百则（各地区不同，大约 200–300 则），付费方案的额度和超出后的价格各地区不同、也会调整（比如台湾的方案 2026-11-01 起调整），以 LINE 官网为准 |
| 适合 | 自用号、小规模、试用 | 正式的客服号 | 客户主要用 LINE 的市场（日本、台湾、泰国等） |

扫码号建议用单独的号码，开着拟真发送（默认开），并保留每会话每小时的回复上限。

### LINE 官方帐号

**怎么接**：

1. 在 LINE Official Account Manager 开好官方帐号，在「设定 → Messaging API」里启用 Messaging API，会在 LINE Developers 建一个 channel。
2. 在 [LINE Developers Console](https://developers.line.biz/console/) 打开这个 channel：「Basic settings」里有 Channel ID 和 Channel secret；「Messaging API」页最下面发一个长期的 Channel access token（long-lived）。
3. 墨鸽「号码 → 添加号」选「LINE 官方帐号」，填这三项（也可以先建号，之后在号的「连接」里填）。
4. 把号的「连接」里显示的 Webhook URL（`<INKDOVE_PUBLIC_BASE_URL>/webhooks/line/<号 id>`）填到 LINE Developers Console 这个 channel 的「Messaging API → Webhook URL」，打开「Use webhook」，可以点「Verify」试一下。
5. 建议在 LINE Official Account Manager 的回应设定里关掉「自动回应讯息」，不然客户会同时收到 LINE 自己的自动回应和墨鸽的回复。

**Channel access token**：墨鸽只支持长期 token，填一次一直用，不会自己换新的。LINE 的开发指南不推荐长期 token（推荐 30 天有效的短期 token 或无状态 token，定期重新签发），墨鸽现在没做自动签发。token 泄露或怀疑泄露时，在 LINE Developers Console 重新签发，旧的作废，再把新的填进号的「连接」里。

**要公网 HTTPS**：LINE 只接受 https:// 的 Webhook URL；发图片时给 LINE 的也是墨鸽的地址，由 LINE 自己来取（LINE 要求放图片的服务器支持 TLS 1.2 及以上）。所以 `INKDOVE_PUBLIC_BASE_URL` 必须是 https:// 开头、公网能访问的地址，墨鸽要放在带证书的反向代理后面（见[部署说明](deploy.md#line-官方帐号要的公网-https)）。不是 https:// 时号的「连接」里有提醒，发图片和文件会直接失败、不发出去。

**回复和推送**：客户每发来一条消息，LINE 给一个 reply token，1 分钟内能用一次，用它回复不计数。墨鸽收到后 50 秒内（留点余量）的第一次发送用它，过了时间、已经用过、或者 LINE 说它无效时改用推送（push），推送算进每月额度。一次回复分成几条发的，只有第一条用 reply token，后面几条和随后发的文件都是推送；人工回复一般超过 1 分钟，基本都是推送；自动回复要等防抖、生成回复和拟真等待，加起来超过 50 秒的也是推送。额度用完时推送发不出去，消息记为发送失败，号的连接状态显示「LINE 本月可推送的消息数用完了…」，下一次推送成功后自动消失；这期间 1 分钟内的回复不受影响。

**发图片和文件**：LINE 没有文件消息，也没有上传接口。1MB 以内的 jpg、png 按图片发（文件说明另发一条文字，在同一次请求里）；其他文件（PDF、Excel、大图等）发成一条文字：文件名和下载链接。图片地址和下载链接都是墨鸽的签名地址，30 天有效，期间拿到链接的人不用登录就能下载这一个文件，见下面「安全设计」。

**和 WhatsApp 号的不同**：

- 客户没有手机号，只有 LINE 的 userId（会话里显示「LINE」，名字从 LINE 的资料取，取不到时显示「LINE 用户」）。号码相关的功能都用不上：回复范围固定是全部客户（没有白名单、黑名单），不能外联群发，转人工的 WhatsApp 通知不能用（用邮件通知）。
- 只处理一对一聊天；群组、多人聊天的消息，以及另一个 channel 当主处理时转来的待命（standby）事件，一律不处理。
- 不能撤回已发出的消息（Messaging API 没有撤回接口）。客户撤回消息时 LINE 推 `unsend` 事件，会话里标「客户已撤回」，和扫码号一样不再给 AI 看，但原文还留给业务员看（LINE 建议撤回的消息以后不再被看到、被使用，见[合规指南](compliance.md#line-官方帐号的规则)）。
- 客户加好友时刷新名字；取消好友或封锁只记日志（之后推送会失败）。贴纸显示成 [贴纸]，位置显示成「[位置] 名称（地址）」。
- 拟真发送开着时，回复前标已读、显示「正在输入」动画（20 秒，发出消息时消失）。标已读要在 LINE Official Account Manager 里开着「聊天」功能才有用（关着时客户的消息自动算已读）；标已读出错（比如 403）时只记一条警告，照常回复。
- 在 LINE Official Account Manager 的聊天里直接回的消息，墨鸽不一定收得到（没有实测过 LINE 会不会把这些发到 Webhook）。建议都在墨鸽后台回，聊天记录才完整。

### Telegram

Telegram 有三种接入方式，客户都没有手机号，只有 Telegram 用户 id。

| | Telegram 机器人 | Telegram Business | Telegram 扫码登录 |
|---|---|---|---|
| 原理 | Telegram 官方 Bot API。客户在 Telegram 中搜索机器人用户名并发起会话 | Telegram 官方 Bot API 的 Business 模式：个人帐号在「设置 → 聊天自动化」中添加机器人，机器人以本人身份收发私聊 | 墨鸽以桌面设备身份登录个人帐号（MTProto 协议，第三方客户端），收发该帐号的全部私聊 |
| 准备 | 在 @BotFather 创建机器人，取得 token | 在 @BotFather 创建机器人并开启 Business Mode；个人帐号在「聊天自动化」中添加该机器人 | my.telegram.org 的 api_id 和 api_hash（可在墨鸽中自动获取）；用手机 Telegram 扫码，或用手机号和验证码登录 |
| 风险 | 官方接口，没有协议层面的封号风险。机器人不能主动给未发起会话的人发消息 | 官方接口。墨鸽会收到该帐号的全部私聊（「聊天自动化」中排除的除外），包括亲友消息；只能回复 24 小时内客户发过消息的私聊 | **有封号风险**：Telegram 对第三方客户端控制的个人帐号限制较严，群发或向陌生人发消息风险高。会收到全部私聊，包括亲友消息。服务器上的登录态文件等同于帐号的钥匙 |
| 费用 | 免费 | 免费（自 Bot API 10.0 起「聊天自动化」不需要 Telegram Premium） | 免费 |
| 适合 | 官网、名片上放机器人链接，作为客服入口 | 以个人帐号对外，希望使用官方接口 | 以个人帐号对外，需要收发全部私聊、不受 24 小时限制 |

三种方式都由墨鸽主动连接 Telegram 取消息（机器人和 Business 用 Bot API 的长轮询 `getUpdates`，扫码登录用 MTProto 长连接），**不需要公网地址和 HTTPS**。中国大陆的服务器连不上 Telegram，需先在「设置 → 代理」开启全局代理（见[全局代理](#全局代理)）；开启后 Bot API 请求、MTProto 连接和 my.telegram.org 的请求都经代理出站，代理不可用时不退回直连。

**Telegram 机器人怎么接**：

1. 在 Telegram 打开 @BotFather，发送 `/newbot` 创建机器人，复制返回的 token。
2. 墨鸽「号码 → 添加号码」选「Telegram 机器人」，填入 token（也可以先建号，之后在号的「连接」里填）。
3. 客户在 Telegram 中搜索机器人用户名，或打开「连接」里显示的 `https://t.me/<机器人用户名>` 链接，即可发起会话。

同一个 token 同时只能有一个程序收消息：墨鸽连接时会删除这个机器人原有的 webhook，别处也在用这个 token 收消息时，两边会互相抢。请为墨鸽单独创建机器人。墨鸽重启后接着取停机期间的消息（Telegram 保留 24 小时）；第一次连接时不处理之前积压的消息。

**Telegram Business 怎么接**：

1. 在 @BotFather 创建一个只给这个号码用的机器人，在 Bot Settings → Business Mode 中开启 Business Mode。
2. 墨鸽「号码 → 添加号码」选「Telegram Business」，填入 token。
3. 保存后「连接」里显示绑定链接。由号主本人在 Telegram 中打开链接，点击「开始」（Start），机器人回复「已绑定到墨鸽」即完成。链接只能用一次，请勿转发。
4. 号主在 Telegram「设置 → 聊天自动化」（英文界面 Settings → Chat Automation）中添加这个机器人。撤回消息需开启删除消息的权限，标为已读需开启读取消息的权限。「连接」里显示当前连接的帐号和各项权限。

墨鸽只处理号主本人的帐号经「聊天自动化」转来的消息；其他帐号把这个机器人加进「聊天自动化」时，「连接」里提示「非号主」，消息不处理。号主在手机上发的消息记为「手机上发的」；墨鸽经机器人代发的消息推回来时不重复保存。需要更换号主时，在「连接」里点「更换号主」，生成新的绑定链接。建议在「聊天自动化」中排除联系人、只处理新聊天，或者对这个号码使用人工回复，避免机器人回复亲友。

**Telegram 扫码登录怎么接**：

1. 取得 api_id 和 api_hash，二选一：
   - 在号的「连接」→「自动获取」中填该帐号的手机号，输入 Telegram 发来的验证码，墨鸽登录 my.telegram.org，读出已有的应用，没有时新建一个名为 Inkdove 的应用。my.telegram.org 没有正式接口，墨鸽按其网页表单发送请求，它改版后可能失效；
   - 自己登录 [my.telegram.org](https://my.telegram.org) → API development tools 创建应用，把 App api_id 和 App api_hash 填进号的「连接」。
2. 在「连接」→「登录方式」中选择：
   - **扫码**：点「扫码登录」，用手机 Telegram 的「设置 → 设备 → 连接桌面设备」扫描页面上的二维码，二维码约 30 秒更换一次；
   - **验证码**：填该帐号的手机号（含国家区号），点「发送验证码」，再输入收到的验证码。验证码一般发到该帐号已登录的 Telegram App（发件人是 Telegram 官方），没有 App 时发短信。
3. 帐号开了两步验证的，再在页面上输入两步验证密码。

登录后，该帐号「设置 → 设备」中会出现「Inkdove」，在手机上结束这个设备即可让墨鸽退出。二维码、验证码或两步验证 5 分钟内未完成时，登录自动停止。

- **收哪些消息**：只收与真人的私聊。群组、频道、机器人、收藏夹（自己）、Telegram 官方通知（777000）、已注销的帐号和服务消息一律不收。第一次登录不导入以前的聊天记录；墨鸽重启后补收停机期间的消息（Telegram 保留的时间有限，停机太久的跳过）。
- **登录态**：存在 `<数据目录>/telegram/<号 id>.session`（目录 700、文件 600），和扫码号的 WhatsApp 登录态一样不单独加密，**持有这个文件就能以该帐号收发消息**，请保护好 `./data` 和它的备份。退出登录、删除号码时先从 Telegram 退出再删除文件。号码配置导出时不包含登录态，导入后需要重新登录。
- **登录失效**：墨鸽每 5 分钟检查一次登录是否有效。在手机上结束了这个设备、或者登录被 Telegram 注销时，号的状态变为「未登录」并说明原因，登录态文件随之删除，需要重新登录。连接 Telegram 失败（比如代理还没准备好）时自动重试，间隔逐次加倍，最长 10 分钟。
- **不保存的内容**：api_hash 只存在 SQLite 里，接口不返回明文；自动获取时用的手机号、验证码和 my.telegram.org 的 cookie，登录用的手机号、验证码、两步验证密码和二维码，都只在内存中使用，不写入磁盘、日志和操作日志。

**三种方式的收发能力**：

| | Telegram 机器人 | Telegram Business | Telegram 扫码登录 |
|---|---|---|---|
| 发送 | 文字最多 4096 字；图片最大 10MB；其他文件最大 50MB；文件说明最多 1024 字 | 同机器人 | 文字、图片、文件 |
| 接收客户文件 | 最大 20MB（Bot API 的下载上限），超过的不保存，会话里注明「文件过大，未保存」 | 同机器人 | 同其他接入方式的存盘上限（64MB） |
| 我方撤回 | 机器人发的消息，发出后 48 小时内 | 需机器人有删除消息的权限：经墨鸽发的要「删除机器人发的消息」，号主在手机上发的要「删除所有消息」；时限按 48 小时计 | 没有时限，对双方删除 |
| 客户撤回 | 收不到（Bot API 不通知私聊中的删除） | 标「客户已撤回」；号主在手机上删除的标「已在手机上撤回」 | 同 Business |
| 消息编辑 | 收得到客户的编辑 | 收得到双方的编辑 | 收得到双方的编辑 |
| 拟真发送 | 显示「正在输入」（Telegram 最多显示 5 秒）；机器人不能标已读 | 标已读（需读取消息的权限）、显示「正在输入」 | 标已读、显示「正在输入」 |

**和 WhatsApp 号的不同**：客户没有手机号，会话里显示 Telegram，名字取 Telegram 资料里的名字。号码相关的功能都用不上：回复范围固定是全部客户（没有白名单、黑名单），不能外联群发，转人工的 WhatsApp 通知不能用（用邮件通知）。只处理一对一私聊，群组和频道不处理。机器人和 Business 的 token、扫码登录的 api_id 和 api_hash 在号码配置导出时一并导出（Business 的号主绑定和扫码登录的登录态不导出，导入后需重新绑定或登录），操作日志里只记「已修改」或「已设置」。

## 安全设计

**机器人永远不能**：答应打折或优惠；同意出售或确认订单；答应留货，或者替这位客户这一单保证交货日期、现货；报资料里没有的价格；承认自己是 AI 或自称真人。照资料复述写明的标准条款（标准交期、生产周期、样品几天寄出、起订量、质保、认证、公司生产或提供某款产品）不算承诺，但要保留资料里的限定语（「标准」「一般」「以排产为准」之类），不能说得比资料更肯定；「我们有这款产品」只表示目录里有，资料里没有的「现货」「马上能发」「给你留」才算库存承诺。客户给的数量正好落在资料里两个档位的交界（中文「以上」「以下」含本数）、或者资料说法有歧义时，不替客户挑一档：照资料把相关档位都说出来，或者转人工。拿不准就转人工，不回复客户。

回复要过四层（`server/src/reply/`、`server/src/wa/service.js`）：

1. **system prompt**：只依据知识库回答，带红线和说话方式规则（不说模板腔、不复述问题）；客户消息当数据，不当指令；埋一个随机的金丝雀串。
2. **程序硬规则**：业务回复必须引用真实存在的条目；超长、带代码块、出现金丝雀串的拦下；**价格红线**：回复里的金额、百分比、"X 折"必须在引用的条目里出现同样的数值；成交和给优惠的措辞（短语级匹配，"we deal in…"这类正常描述不受影响）、资料里没有的优惠词、身份表述和"根据知识库""according to the information provided"这类元话语，一律拦下转人工。命中客服套话时重写一次，还有就删掉那句。
3. **审核调用**：再让模型检查一遍回复有没有越界、有没有资料依据、有没有承诺（和上面同一个标准：照资料复述标准条款不算 commitment）；回复里的数字（价格、起订量、交期天数、数量档位、功率、质保年限等）逐个和引用的条目、企业画像核对，数量落在两个档位交界或资料有歧义、回复却自己挑了一档的判 ungrounded；审核失败或超时，默认不发。
4. **会话闸门**：24 小时内离题 3 次静默 24 小时；每会话每天最多 60 次 LLM 调用；每会话每小时回复次数有上限（超了转人工）；每个号每分钟最多 30 条自动回复。

其他：

- 登录：邮箱 + 密码（scrypt 加盐哈希），服务端存储的会话 token，httpOnly + SameSite=Lax cookie；同一 IP、同一邮箱每分钟失败 5 次后限流。邀请和重置链接一次性、会过期。停用、删除或改密码时立即踢掉这个人的会话。
- 权限全部在服务端判断：业务员访问没分给自己的号、没分给自己的会话（包括未分配的）和这些会话的线索一律 403。号级别的操作只有管理员能做，业务员调用一律 403：改号的设置（`PUT /api/accounts/:id` 整个拒绝，含回复方式、人设、回复范围、名单、通知）、扫码连接 / 取二维码 / 配对码 / 登出、Telegram 的登录 / 验证码 / 两步验证密码 / 退出登录 / 更换号主 / 自动获取 api_id、测试通知、导出客户线索 CSV。业务员读号时，Meta 的 `verifyToken` 返回 null，通知的收件邮箱和号码返回空，客户名单和联系方式不经业务员流出。
- Webhook：WAHA 校验 `X-Webhook-Hmac`（HMAC-SHA512），Meta 校验每个号自己的 `X-Hub-Signature-256`，LINE 校验每个号自己的 `X-Line-Signature`（用这个号的 Channel secret 对原始请求体算 HMAC-SHA256，base64）。LINE 号没填 Channel secret 时拒绝接收。Telegram 的三种接入方式都由墨鸽主动去取消息，不开放回调地址。
- 密钥（LLM key、向量服务的 key、重排服务的 key、翻译服务的密钥和 DeepLX 的地址、Meta token 和 app secret、LINE 的 Channel secret 和 Channel access token、Telegram 机器人的 token 和扫码登录的 api_hash、SMTP 密码、Resend key、代理密码、全局代理的订阅地址和节点）存在 SQLite 里，接口不回传明文、不写日志。所以要保护好 `./data` 和它的备份。Telegram 扫码登录的登录态文件也在 `./data/telegram/` 里，见上面的 [Telegram](#telegram)。
- 文件下载链接：`/internal/files/<id>?token=…` 不要求登录，靠 token（`INKDOVE_SESSION_SECRET` 算的 HMAC 签名，只对这一个文件、过期前有效）。给 WAHA 取文件的是 compose 内网地址、10 分钟有效；LINE 号发图片和文件时用的是公网地址（`INKDOVE_PUBLIC_BASE_URL` 开头）、**30 天有效**：链接发给了客户，客户转给别人，别人 30 天内也能下载。想提前作废，只能在「文件」页删掉这个文件，或者换 `INKDOVE_SESSION_SECRET`（影响大：所有人都要重新登录，所有链接一起作废）。别把不想外传的文件用 LINE 发。
- 网址抓取有 SSRF 防护（每一跳重定向都重新解析、拒绝内网地址）。
- 操作日志（「管理 → 操作日志」，[详细规则](features.md#操作日志)）：
  - **记什么**：成员在后台做的所有改动（号、会话分配、知识库、产品资料、客户线索、外联、设置、成员、在线更新），导出号码配置和客户线索 CSV，登录成功和失败、退出、改密码、接受邀请。每条记时间、谁（当时的名字、邮箱、角色）、做了什么、对象、改之前和改之后、成功还是失败（失败原因和状态码，越权的 403 也记）、IP。
  - **不记什么**：给客户发的消息和文件（聊天记录里有，发送人记在消息上），页面自动发的请求，没登录的请求，webhook 和后台任务，只读的查看。**密钥、密码、token、代理密码、订阅链接只记「已修改」，绝不记明文**；登录失败不记输入的密码，邮箱栏里填的不像邮箱时也不记原文；邀请和重置链接不记；长文本只记字数；请求体从不整个存。
  - **谁能看**：只有管理员，业务员调用返回 403。没有改和删的接口，谁都改不了、删不掉。
  - **保留多久**：默认 365 天，`INKDOVE_AUDIT_RETENTION_DAYS` 可改，过期的每天自动清掉。日志和其他数据一起存在 `./data` 的 SQLite 里。
- 向量检索（默认关闭）开着时，知识库条目的标题、内容和标签，以及回复时的客户消息（本次加最近几条，最多 1500 字）会发给设置里的向量服务算向量；用「和回复模型同一个」时发给回复模型的服务商，单独配置时发给那个服务。用本机的 Ollama 时这些数据不出本机。向量服务的密钥和 LLM key 一样只存在 SQLite 里，接口不回传明文、错误信息和日志里不带。
- 重排（默认关闭）开着时，知识库超过 4 万字、要检索的那些回复，会把客户消息（本次加最近几条，最多 1500 字，和算查询向量的同一段）和检索出来排在前面的最多 40 条知识条目（每条的标题、内容和标签，最多 2000 字）发给设置里的重排服务（Jina、Cohere、硅基流动、Voyage，或者自己部署的 vLLM、Xinference）。不带号码和客户名字。自己部署在本机或内网时这些数据不出去。重排服务的密钥和 LLM key 一样只存在 SQLite 里，接口不回传明文、错误信息和日志里不带。
- 一键翻译默认用回复模型（AI 翻译），数据去向和回复一样。选「翻译 API」时，业务员点翻译的那段话，和客户最近几条文字消息里最多 300 字（用来判断客户的语言，客户每发一次新消息最多发一次），会发给所选的翻译服务（DeepL、谷歌、Azure、百度、火山等）；不带号码和客户名字。消息译成中文也一样：点「翻译」的那条消息、自动翻译的推荐回复和转人工草稿正文，会发给所选的翻译服务（AI 翻译方式下发给回复模型）；原文本来就是中文的不发。译文存在 SQLite 里（消息的 `translation` 列、草稿里的 `zh`）。DeepLX、LibreTranslate 自己部署时数据不出自己的服务器；网上公开的 DeepLX 地址能看到发过去的每一句话，不建议用。翻译服务的密钥只存在 SQLite 里；DeepLX 的地址常带令牌，按密钥处理，接口只返回协议和主机。错误信息、日志里都抹掉密钥。
- 首页的 AI 助手（见[功能说明](features.md#ai-助手)）用回复模型，发给模型的有：system prompt（现在的时间和时区、提问人的名字和角色）、问题、这个对话最近 6 轮的问答文字、工具的定义，以及这次查到的工具结果。工具结果只含提问人有权限看的数据：会话的客户名字和号码、聊天记录（每条最多 500 字，一次最多 40 条）、客户线索（含邮箱、公司、国家等字段）、知识条目、产品资料的名称和描述、号的名称和状态；管理员还可能查到成员的名字、邮箱和模型用量。每个工具结果最多 8000 字符。客户的话在结果里套上 `<customer_message>` 当不可信数据处理；工具都是只读的，模型被带偏也改不了数据、发不了消息。开着向量检索时，查知识库的关键词也会发给向量服务；开着重排时，查知识库的关键词和查到的知识条目也会发给重排服务（知识库超过 6000 字时）。第一次用某个模型配置、模型又没调工具就回答时，会多发一次不带任何业务数据的检查请求（只问它会不会调用一个叫 `inkdove_ping` 的工具）。助手的问答存在 SQLite（`assistant_chats`、`assistant_messages`），只有提问的人自己看得到。
- 屏蔽词（默认关闭）：开着时，我方发给客户的文字发出前在本机比对词表，不发给任何外部服务。查的是业务员和管理员在后台发的消息、文件说明、一键翻译的原文，机器人的自动回复，通知号码上转发的话和 `/d` 发的草稿，外联的开场消息，命中就不发；机主在手机上发的只能事后记下来。客户发来的消息不查。命中时在 SQLite 的 `blockword_hits` 表存一行：谁发的（成员名，或机器人、机主手机、通知号码）、哪个号和会话（联系人名字）或外联任务、时间、命中的词和位置、**原文**（最多 10000 字），以及谁点了「知道了」。词表、命中记录和原文只有管理员能看，弹窗提醒也只发给管理员；业务员调这些接口一律 403，发消息被拦时只看到命中了哪个词。记录不会自动删除。「AI 扩充」是管理员手动点的：选中的种子词和词表里已有的词（最多 200 个）会发给回复模型，不带任何客户数据。
- AI 发言检查（默认关闭，在「设置 → 屏蔽词」里单独打开，要先配好回复模型）：开着时，我方发给客户的文字（后台发的消息和文件说明、一键翻译的原文、自动回复、通知号码上转发的话、外联开场消息、机主在手机上发的）会发给设置里的回复模型，看有没有辱骂、威胁这类说法。后台查的那部分每条还带上前面最多 4 条消息当上下文，**包括客户发来的话**（每条最多 300 字）；AI 翻译和自动回复是在翻译、审核那一次调用里顺带看，不多发数据。撤回了的消息不发。结果只用来提醒管理员，不拦也不改任何消息；发现问题时和屏蔽词命中一样在 `blockword_hits` 存一行（原文、问题类别、说明、引用），查过的文字另存哈希和结果（`conduct_cache`，只留 24 小时，不存原文）。业务员只在会话页看到一句「发出的消息会做合规检查」，看不到结果。

## 代理中继（F13）

WAHA 的 GOWS 引擎只会走 HTTP 代理：它把代理地址固定拼成 `http://host:port`（WAHA 源码 `src/core/engines/gows/session.gows.core.ts` 的 `getProxyUrl`）。为了让四种协议都能用，inkdove 做协议转换：

- 上游是 **http**：直接交给 WAHA，`config.proxy = {server: "host:port", username, password}`（账号密码先 URL 编码）。
- 上游是 **https / socks4 / socks5**：inkdove 为这个号起一个**本地 HTTP CONNECT 中继**，WAHA 的代理指向 `inkdove:<端口>`，账号密码是这个号专属的随机凭证（存在库里，不出现在接口里）。中继收到 CONNECT 后：
  - https：先用 TLS 连上代理本身，再发 CONNECT；
  - socks4 / socks5：用 [`socks`](https://www.npmjs.com/package/socks) 包建立连接。
- 中继只放行 CONNECT（其他方法 405），必须带正确的 `Proxy-Authorization`（否则 407），上游连不上返回 502。
- 端口从 `INKDOVE_PROXY_RELAY_PORT_BASE`（默认 18000）开始，每个扫码号建号时分一个。容器里绑 `0.0.0.0`，但 compose 不映射这些端口，只有同一内网的 WAHA 能连到。
- 号的代理一改，中继就重启，同时 `PUT /api/sessions/{name}` 更新 WAHA session（运行中的 session 会被 WAHA 自动重启，不用重新扫码）。inkdove 重启时按库里的配置重新拉起所有中继。删除号时关掉它的中继。
- "测试代理"仍然从 inkdove 直连上游代理去测，不经过中继。
- 选了「用全局代理」的号不起中继：WAHA 的代理直接指向 `inkdove:<INKDOVE_GLOBAL_PROXY_PORT>`（mihomo 的混合端口，HTTP 代理，GOWS 能用），账号密码是全局代理的那组（见下一节）。全局代理的端口或账号密码变了时，同样 `PUT` 更新这些号的 WAHA session。这时"测试代理"测的是全局代理。

## 全局代理

「设置 → 代理」开着时（默认关），墨鸽自己连外网的请求经机场节点出去，用法见[功能说明](features.md#全局代理)。

**数据怎么走**：

```
墨鸽进程 ──(本机 127.0.0.1:17890，HTTP CONNECT，不要密码)──> mihomo（墨鸽的子进程）──> 机场节点 ──> 目标网站
WAHA（选了「用全局代理」的号）──(compose 内网 inkdove:17890，要账号密码)──┘
```

- 墨鸽这边换掉了 Node 自带的全局 `fetch` 的出口（还是 Node 自带的 undici，见下面），`node:http` 的媒体下载和 nodemailer 的 SMTP 也按同样的规则走。连 mihomo 时 CONNECT 里写的是**域名**，不在本机解析：本地 DNS 看不到墨鸽访问了哪些域名，域名由节点那边解析。
- 直连的：本机、内网和保留地址、不带点的主机名、`.localhost` / `.local` / `.internal` / `.home.arpa`、WAHA 和更新助手的地址，以及管理员填的「直连地址」。只按主机名判断。下载订阅也总是直连。
- **开着时代理起不来或连不上，请求直接失败，不退回直连**：选全局代理多半是不想让服务器本身的 IP 出现在对方那里，偷偷改直连会把它暴露出去。设置页的运行状态会显示原因。
- 网址抓取的 SSRF 防护照旧：先在本机解析，解析出内网地址的一律拒绝，再经代理去取。

**机场（节点的运营方）能看到什么**：经代理的每个连接的目标域名和端口、连接的时间和流量大小。HTTPS 的内容是加密的，机场看不到（模型、向量、翻译、Resend、Meta、GitHub 都是 HTTPS）；**接口地址填的是 http:// 的（比如自己在公网上搭的、没有 TLS 的模型服务）内容也能看到**，SMTP 走 SMTPS 或强制 STARTTLS，加密之后的内容看不到。目标网站看到的是节点的 IP。机场还知道订阅地址里带的你的机场账号。

**凭证存在哪**：

- 订阅地址（通常带着机场账号的 token）、粘贴的配置解析出的节点（服务器、端口、密码、uuid 等）存在 SQLite 的 kv 表里（`settings` 里的 `proxy` 和 `proxy_nodes`）。接口只回「订阅地址有没有设」、节点数和节点名，不回地址、服务器和密码；粘贴的原文不保存。下载订阅出错时，错误信息里不带订阅地址（主机名、路径、参数都不带）；mihomo 的报错进日志和状态之前，抹掉节点的服务器、密码、uuid、各种 key。
- mihomo 的配置文件写在 `./data/mihomo/config.yaml`（目录 700、文件 600），里面有节点的明文、控制接口的 secret 和 WAHA 用的账号密码。备份 `./data` 时一并保护好。
- mihomo 的控制接口（测速、查当前节点用）只听 `127.0.0.1` 的随机端口，带每个进程随机生成的 secret。
- 混合端口 17890（`INKDOVE_GLOBAL_PROXY_PORT`）在容器里绑 `0.0.0.0`，因为 WAHA 要从 compose 内网连进来；从本机连不要密码，从别处连必须带账号密码。compose 不映射这个端口，不要把它映射到宿主机。
- WAHA 连它用的是**所有号共用的一组**随机账号密码（kv 表 `proxy_meta`，进程重启不变），不是每个号一组：mihomo 的账号写在配置文件里，每个号一组的话，一个号开关「用全局代理」就得重启 mihomo，所有经它的连接（别的号、正在调的模型）都会断一下。这组账号密码只给 compose 内网里的 WAHA，不出现在接口里。

**和 npm 的 undici 的关系**：墨鸽依赖的 npm 包 undici 7.30 有一个会让进程崩溃的 bug，所以全局 `fetch` 一直用的是 Node 自带的 undici（`server/src/builtin-fetch.js`）。全局代理换出口时，用的仍然是 Node 自带的那一份 undici 的 `Agent`（从启动时的全局 dispatcher 上取它的构造函数），自己建 CONNECT 隧道再在隧道里做 TLS，不用 npm undici 的 `ProxyAgent`；关掉时换回原来那个 dispatcher。`server/test/global-proxy.test.js` 里有测试确认换上去的不是 npm undici 的对象。
