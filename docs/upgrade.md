# 升级说明

日常升级（拉新镜像、重建容器）见 [README 的「升级」](../README.md#升级) 和 [在线更新](online-update.md)。这里记的是跨版本时数据结构或行为有变化、要多留意的地方，按时间先后排。

## 从第一期升级

- 必须新增 `INKDOVE_ADMIN_EMAIL`。第一次启动时用它和 `INKDOVE_ADMIN_PASSWORD` 建管理员；旧的登录 cookie 全部失效，重新登录即可。
- 第一期的通道设置会自动迁移成一个叫「默认号」的号：自动回复开关、回复范围、名单、代理和通知都带过去，旧会话挂到这个号下。扫码号沿用原来的 session 名（第一期设过 `INKDOVE_WAHA_SESSION` 的，升级时保留这个变量），不用重新扫码。旧的 SMTP 设置挪到全局"发信方式"。
- **Meta 号的回调地址变了**：从 `/webhooks/meta` 改成 `/webhooks/meta/<号的 id>`，旧地址已删除。升级后去 Meta 后台把回调地址换成号详情页显示的新地址。
- 产品资料库、缺口来源、语音图片这些新增的表和列在启动时自动加上，不改动已有数据。已经在待处理的会话会从最近一条未回复的客户消息补上 `pendingReason`。WAHA 容器要按新的 compose 加上两个环境变量（见[部署说明](deploy.md#部署说明)），重建一次 waha 容器即可，不用重新扫码。

## 升级到按客户分配

- 会话的可见范围从"按号"改成"按客户"：业务员只看得到分给自己的会话（还要有这个号的权限），管理员仍然看得到全部。
- 升级后第一次启动时自动迁移一次（库里记了标记，之后不再跑）：已有的会话，如果它所属的号**恰好只有一个**启用中（没停用）的业务员有权限，就分给这个业务员；同一个号有两个及以上业务员、或者一个都没有的，保持未分配，只有管理员看得到，要管理员在会话页分配（可以多选批量分配）。迁移之后新来的会话一律未分配。

## 升级到推荐回复（三种回复方式）

> v0.3.1 起推荐回复改为只手动触发，见下一节。

- 号的「自动回复」开关换成了回复方式 `replyMode`（`off` 关闭 / `suggest` 推荐回复 / `auto` 自动回复）。**已有的号行为不变**：原来开着自动回复的是 `auto`，关着的是 `off`，不会突然变成推荐回复、多花模型费用。只有升级后新建的号默认是 `suggest`。库里不用迁移，读号时按旧的开关换算，下次保存号的设置时改存 `replyMode`。
- 接口兼容：号对象照旧返回 `autoReply`（等于 `replyMode === 'auto'`），`PUT /api/accounts/:id` 也照旧接受 `autoReply`（true → `auto`，false → `off`），同时给了 `replyMode` 时以 `replyMode` 为准。
- 号码配置导出文件改带 `replyMode`，不再带 `autoReply`。升级前导出的老文件照样能导入：只有 `autoReply` 时按上面的规则换算，两个都没有的按新建号的默认值 `suggest`。
- **业务员的权限收紧了**：升级后业务员不能再改号的任何设置（回复方式、人设、回复范围、名单、通知）、不能扫码连接或登出号、不能测试通知、不能导出客户线索 CSV，这些都只有管理员能做；读号时也看不到 Meta 的 verify token 和通知的收件人。以前让业务员自己扫码连号的，升级后改由管理员连。

## 升级到 v0.3.1（推荐回复改为手动）

- 回复方式只剩两种：`off`「人工回复」（新建号的默认值）和 `auto`「自动回复」，去掉了「推荐回复」模式。客户来消息时不会再自动起草、不调用模型；需要时在会话页点「推荐回复」（或草稿框上的「换一条」）手动要一条，任何回复方式下都能用。
- v0.3.0 里设成「推荐回复」（`replyMode: suggest`）的号，升级后自动变成「人工回复」（`off`）：库里不用迁移，读号时按 `off`，下次保存号的设置时改存 `off`。
- 接口兼容：`PUT /api/accounts/:id` 收到 `replyMode: "suggest"` 按 `off` 处理（兼容 v0.3.0 的客户端），其他不认识的值照旧 400。号对象照旧返回 `autoReply`（等于 `replyMode === 'auto'`）。
- 号码配置导入：文件里 `replyMode` 是 `suggest` 的按 `off`；只有 `autoReply` 的老文件 true → `auto`、false → `off`；两个都没有的按 `off`。导出只写 `off` 或 `auto`。
- v0.3.0 自动起草时留下的「已生成推荐回复」（`suggested`）记录照常显示，只是不再产生新的。
- 客户发来的图片、视频、语音、文件从这一版起存进 `./data/media`，会话里能直接看。**升级前收到的消息没有存**（WAHA 只留 3 分钟，早就没了），照旧只显示 [图片] 这样的文字，去手机上看。`./data/media` 不自动清理，客户发得多时留意磁盘。
- 数据库不用手动迁移；预约更新的记录存在 kv 表里，回滚到旧版本不影响（旧版本不认这两个键，直接忽略）。

## 升级到知识库全文索引

- 回复时不再每次扫一遍整个知识库，改用全文索引挑条目（规则见[「知识库怎么带进回复」](features.md#知识库怎么带进回复)）。知识库不超过 40000 字符的照旧全带，回复不变。
- **升级后第一次启动时自动建索引**，日志里有一行「知识库全文索引……已重建 N 条，用时 …ms」。几百条的知识库不到 1 秒；5000 条（约 380 万字）约 0.5 秒，3 万条（约 2300 万字）约 3.5 秒，这段时间服务还没开始监听，等日志里出现监听端口再访问。之后启动只核对一下，不重建。
- 数据库不用手动迁移。新增的是全文索引表 `entries_fts`（只存索引、不另存一份原文）、记录索引对应哪个条目版本的小表 `entries_fts_state`、一个条目索引和 kv 里的 `entries_fts_version`。库文件大约多出条目正文字节数的 85%：测试库 5000 条、约 380 万字（正文 9MB）从 13.6MB 变成 21.3MB，3 万条、约 2300 万字从 79.5MB 变成 124.8MB（都是 VACUUM 之后的大小）。每次在线更新前的数据库备份也跟着大这么多。
- 回滚到旧版本不影响：旧版本不认这张表，照常读写条目。回滚期间改过、加过、删过条目的，再升级回来启动时会发现索引对不上，自动整个重建一次。
- 客户和知识库语言不同、按原话检索命中太少时，会多调一次模型改写检索词（`llm_calls` 记 `kb_search`，看板里叫「知识库检索改写」），计入每会话每天 60 次。知识库不超过 40000 字符的不会调。

## 升级到 v0.3.2（可选的向量检索）

- 新增「设置 → 向量检索」，**默认关闭**，不开就和以前完全一样，不多调任何接口。规则见[「知识库怎么带进回复」](features.md#知识库怎么带进回复)。
- 打开后后台会把全部条目算一遍向量（会调用向量接口、按服务商价格计费，`llm_calls` 记 `embedding`，看板里叫「向量检索」），设置页能看到进度。知识库不超过 40000 字符时回复用不上它，不用开。
- 数据库不用手动迁移，启动时自动建 `embeddings` 表。开了以后库文件会变大：向量按 int8 量化存，1024 维时每段约 1.4KB（含其他列和索引），3 万段大约多 42MB，在线更新前的数据库备份也跟着大。关掉不会删已经算好的向量（再打开不用重算）；换了向量模型的，新模型全部算完后自动删掉旧的。
- 回滚到旧版本不影响：旧版本不认这张表。
